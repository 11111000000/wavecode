# Решения: math-coding v5 (`spec.json`) вместо 3.3 (`decisions/*.yaml`)

**Статус:** действующая политика фиксации решений wavecode.
**Ядро:** `mathc` 5 (релиз `v5.0.2`), схема `spec.json` (`schema_version: 5`).

---

## 1. Почему

Решения в wavecode долгое время фиксировались в формате math-coding **3.3** —
по одному YAML-файлу `decisions/<id>.yaml` на решение, с проверкой ядром
(`mathc validate`, `mathc self-check`).

Ядро 3.7, на которое была рассчитана эта схема, **больше не доступно**: релиз
`edge` на GitHub отдаёт 404, а формат `decisions/*.yaml` ядро 5 не читает вовсе
(«v3/v4 formats remain removed. spec.json schema_version 5 only.»). То есть
действующий CI-гейт math-coding был неисполняем: он звал команды, которых
больше нет.

Ядро 5 — это принципиально другая модель, а не новая версия того же формата:

| | 3.3 | 5 |
|---|---|---|
| носитель | `decisions/<id>.yaml` на решение | один `spec.json` в корне |
| единица работы | решение-файл | **утверждение (claim)** с границами и условиями подтверждения |
| проверка | `mathc validate` + `mathc self-check` | `mathc run` (verdict + карта покрытия) |
| связь с источником | `axiom_link` | `source` с **дайджестом**: изменение источника делает claim «outdated» |

## 2. Что меняется в репозитории

1. **Активная запись решений — `spec.json`** в корне репозитория: цель
   (`goal`) и утверждения (`claims`). Каждое утверждение несёт текст,
   предметную область (`scope`), ссылку на источник решения, условия
   подтверждения (`requirements`), **опровергатель** (`falsifier`) и
   **отрицательный контроль** (`control`).
2. **`decisions/*.yaml` (133 файла) остаются историческим реестром ADR.**
   Они больше не пишутся и не валидируются ядром; новые решения не создаются
   в этом формате. Их роль — источник мотивации: claim'ы ссылаются на них
   через `source` с дайджестом, поэтому правка старого решения переводит
   связанный claim в состояние «outdated» и требует явного пересмотра
   (`mathc review-source`).
3. **Гейт CI переезжает на ядро 5**: `.gitverse/workflows/math-coding.yml`
   ставит `mathc` из релиза `v5.0.2` и запускает `mathc run`.
   Коды возврата: `0` — зелёный вердикт, `1` — красный, `3` — неопределённый.
4. **`policy.json`** защищает `spec.json` и `decisions/`: изменение этих путей
   требует явного разрешения (`mathc authorize --by az --reason "..."`).

## 3. Правило утверждения

Утверждение считается подтверждённым только если:

- у него есть **исполняемая проверка** (`verifier:COMMAND`) — команда, которая
  принимает предмет, когда утверждение истинно;
- у него есть **отрицательный контроль** (`control`) — команда, которая
  меняет предмет так, что проверка её отвергает. Ядро исполняет контроль в
  **изолированной копии** репозитория и требует, чтобы проверка после
  мутации упала.

Проверка без контроля даёт «not-run» → «inconclusive» → вердикт `unknown`.
То есть утверждение без опровержимого контроля **не может** стать зелёным.

Отсюда практическое следствие: verifier'ы не могут рассчитывать на
`node_modules` — изолированная копия это `git clone`, без установленных
зависимостей. Поэтому все проверки wavecode живут в
`scripts/check-invariants.mjs` (только stdlib Node) и проверяют
**архитектурные инварианты**, а не код:

| режим | что проверяет |
|---|---|
| `layering` | слои не тянут друг друга (то же, что enforce eslint) |
| `console` | `domain/` и `application/` не пишут в глобальный `console` |
| `camera` | камера включается только явным действием пользователя |
| `deploy` | ни один CI-workflow не деплоит |
| `secrets` | в репозитории нет значений секретов |
| `decisions` | каждое решение в `decisions/` сохраняет свои ключи |
| `spec` | `spec.json` цел, у каждого claim'а есть verifier и контроль |
| `gate` | CI-гейт использует ядро v5 и зовёт `mathc run` |
| `term` | термин-бокс раскладывает жесты по разным строкам сетки |

**Разделение гейтов.** `.github/workflows/ci.yml` проверяет здоровье кода
(typecheck, lint, юнит-тесты, сборка, e2e). Гейт math-coding проверяет
**обоснованность**: только инварианты, зафиксированные в `spec.json`, и
связь каждого утверждения с живым источником решения.

## 4. Как работать с утверждениями

```bash
export PATH="$HOME/.local/bin:$PATH"

mathc goal "AIM" "SCOPE[,SCOPE]" "OWNER"          # цель задаёт человек
mathc add ID "TEXT" "SCOPE" "FALSIFIER" fact \
  --requirement "verifier:CMD" --control "BREAK_SUBJECT" [--source ADR]
mathc run                                           # 0 = green, 1 = red, 3 = unknown
mathc map | mathc next | mathc context              # карта покрытия и следующий шаг
mathc install                                       # блок math-coding в AGENTS.md
```

Ограничения ядра 5, которые нельзя обходить ручной правкой ради зелёного
результата:

- claim не может выйти за область цели (`goal.scope`);
- у claim должен быть минимум один `verifier` и `control`;
- `control` обязан менять **предмет** claim'а и ломать его проверку;
- `waive` — только с автором, причиной, сроком и recovery.

## 5. Что осталось за кадром

- 133 файла в `decisions/` не конвертируются в claim'ы: их verifier'ы —
  идентификаторные метки (`vitest-run-*`, `pnpm-ui-*`, `playwright*`), реальную
  команду из такой строки не восстановить. Конвертация «на глаз» дала бы
  утверждения, которые никогда не могут быть подтверждены, — это хуже, чем
  явный исторический реестр.
- `attestations/` (формат 3.3) и `schemas/decision.json` (схема 3.3) остаются
  историческими артефактами; активной поверхностью они не являются.
- Ядро 3.7 и его `rehash`/`validate`/`self-check` в проекте больше не
  используются: соответствующие вызовы в гейте удалены.
